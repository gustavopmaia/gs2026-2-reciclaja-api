[1] Rascunho do contrato OpenAPI (2_contrato_api.yaml)
Responsável: Gustavo Maia · Revisão: Gabriel Fidalgo
----------------------------------------------------------------------
PROMPT:
"Tenho estes endpoints: GET /v1/points (filtros material, bairro, status,
limit/offset), GET /v1/points/{id}, POST /v1/ask. Gere um esqueleto OpenAPI 3.1
com um schema de erro único para 400/404/422/503 e paginação com campo next."

O QUE APROVEITAMOS:
- Estrutura de components/responses reutilizáveis (BadRequest, NotFound...).
- Uso de type: [string, 'null'] do OpenAPI 3.1.

O QUE DESCARTAMOS / MUDAMOS:
- A IA sugeriu "status: string" livre: trocamos por enum (aberto, lotado, manutencao, fechado).
- A IA misturava 400 e 422 para tudo: definimos a regra (path/query/JSON quebrado = 400,
  corpo bem formado mas inválido = 422) e documentamos no info.description.
- Acrescentamos sozinhos: campo mode (llm/fallback/refused), refusal_reason, disclaimer,
  data_source e Retry-After no 503.

COMO VALIDAMOS: openapi-spec-validator (OK) + teste test_contrato_openapi_valido +
assert_contract validando as respostas reais contra o YAML.

Responsável: Gustavo Maia

CONTEXTO: o primeiro run falhou no passo do gitleaks com
"fatal: ambiguous argument '6c7a926...^..0c9164b': unknown revision".

PROMPT: "Por que o gitleaks-action falha no primeiro push de um repositório novo?"

primeiro commit do repositório não tem pai.

(commit "CI: gitleaks via CLI varrendo todo o historico"). Run seguinte: verde.
